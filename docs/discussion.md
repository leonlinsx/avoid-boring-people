# First-party article discussion

Article discussion on `leonlins.com` is a small first-party system. It replaced
Giscus (GitHub Discussions in an iframe) so that readers no longer need a GitHub
account, so that no third party receives reader activity, and so that the site
owns the data and the rendering.

The goals were deliberately narrow:

- one article discussion, accountless, available to any reader
- plain-text comments with one level of replies
- self-service edit and delete for 30 minutes
- spam resistance without collecting IP addresses
- local-only moderation, with no admin dashboard or admin API

The system is not a commenting platform. There is no voting, no threading
beyond one reply level, no notifications, no email collection, no commenter
accounts, no search, and no analytics subsystem.

## What a reader sees

Article pages stay statically generated. `src/components/Discussion.astro`
renders the discussion shell into the built HTML, so the heading, the prompt, the
form, and the private-email link are present before any JavaScript runs. Two
build-time caveats are worth stating: the form is only in the HTML when
`PUBLIC_TURNSTILE_SITE_KEY` was set for the build, and the shell is
server-rendered by Astro's Preact integration rather than by hand.

Only the island in `src/components/DiscussionIsland.tsx` is hydrated, and it is
hydrated on `client:visible`: an article view fetches neither the island's
JavaScript nor any comment data until the reader reaches the section. The
reserved `min-height` covers the loading state when they do.

- Heading: `Discussion`, with a count only once at least one published comment
  exists (`Discussion · 3`). The system never renders `0 comments`.
- Prompt: the optional frontmatter `discussionPrompt` for the article, or the
  default `What did I miss?`, shown above the form rather than as a field label
  so it stays visible while replying. No article has to set it.
- Invitation: `Thoughtful disagreements, additional evidence, and different ways
of looking at the problem are welcome.`
- Fields: a required display name and a plain-text body (3000 characters
  maximum, shown with an `Add to the discussion…` placeholder), plus a hidden
  honeypot field that only automated submitters fill.
- Replies: one level. Reply is offered on top-level comments only.
- Author comments render the display name followed by an `Author` badge. The
  badge comes from the `is_author` column, so a public visitor who names
  themselves "Leon" gets no badge.
- Empty state: `No comments yet. Add the first one.` with the form as usual.
- If the API is unreachable, the list area shows `Comments could not be loaded.
Refresh the page to try again.` and the article is unaffected. A failed post
  reports `Discussion is temporarily unavailable.` instead, because advising a
  refresh there would discard what the reader wrote.
- When the build had no Turnstile site key, `Discussion is temporarily
unavailable.` stands in for the form, so a reader never sees a form that could
  not submit.
- A private path sits below the form: `Prefer a private conversation? Email
Leon.` The mailto link carries the article slug as its subject. Commenters are
  never subscribed to the newsletter and are never asked for an email address.

Layout shift is bounded rather than eliminated: the discussion list reserves a
modest `min-height` so the loading state does not jump from zero height. A long
thread expands the page below the reader, which is acceptable.

## Data model

One table, `migrations/comments/001_initial.sql`:

| Column                     | Notes                                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `id`                       | `UUID` primary key, generated by the database. Public identifiers reveal nothing about volume or ordering. |
| `post_slug`                | Article slug the comment belongs to.                                                                       |
| `parent_id`                | `NULL` for top-level comments, otherwise the top-level comment being replied to.                           |
| `author_token_hash`        | SHA-256 of the reader's browser token. The token itself is never stored.                                   |
| `author_name`              | Display name or pseudonym.                                                                                 |
| `body`                     | Plain text.                                                                                                |
| `status`                   | `published` or `hidden`. Hidden comments are never returned publicly.                                      |
| `is_author`                | Set only by the operator CLI. Public input can never set it.                                               |
| `created_at`, `updated_at` | Timestamps.                                                                                                |

Ownership, rate limiting, and moderation are expressed entirely in this table:
there is no identities table, no sessions table, no rate-limit table, and no
moderation log. Rate limiting counts recent rows for the same token hash, and
ownership compares the hashed token. Check constraints mirror the application
limits (name ≤ 60, body ≤ 3000, slug ≤ 120) as a backstop for any writer that
bypasses the API.

## Identity and the edit window

There are no accounts. On the first successful comment, the server generates 256
bits of randomness, returns it as an `HttpOnly; Secure; SameSite=Strict` cookie
(`leonlins_comment_token`, one year), and stores only its SHA-256 hash. The
cookie is never exposed to JavaScript and is never logged.

The cookie identifies a browser, not a person. Clearing cookies loses the
ability to edit or delete earlier comments — that is accepted, since moderation
is available locally. Ownership grants exactly two things inside a 30-minute
window measured by the database clock, not the browser's:

- `PATCH` replaces the body. The display name is not editable, and an edit never
  grants or removes the author badge.
- `DELETE` removes the comment. If it has no replies the row is deleted; if it
  has replies the name, body, and token hash are nulled and the row remains as
  `[comment deleted]` so replies keep their place in the thread.

Outside the window, or from a different browser, ownership checks simply fail
with `not_owned`; there is no separate expiry state to reason about.

## Abuse controls

Four independent controls, and no IP addresses anywhere:

1. **Cloudflare Turnstile**, verified server-side against
   `TURNSTILE_SECRET_KEY` before anything is written. Verification is
   single-use: the island resets the widget after every attempt. An outage
   fails closed, because no unverified comment is ever accepted.
2. **Honeypot.** The `website` field is off-screen and hidden from assistive
   technology. A filled field is silently discarded: the request is answered with
   `200 {ok: true}` and no comment, no cookie, and no database write, so an
   automated submitter learns nothing beyond the fact that the request was not
   rejected outright.
3. **Rate limiting** from the `comments` table: about 3 comments per token
   hash per 10 minutes, counted across all articles and including hidden rows.
   The check is a count followed by an insert and not one transaction, so a
   concurrent burst can slip a request or two past it; Turnstile's single-use
   tokens are the real limit and this is friction on top.
4. **Origin checks.** The middleware rejects cross-site form submissions, and
   every state-changing handler re-checks the `Origin` header against the
   canonical site origin (`src/lib/site-origin.ts`) rather than against the
   request `Host`, which a proxy or caller could influence.

No `remoteip` value is ever sent to Turnstile, and no identifier is derived from
a request address. If token-based abuse becomes real, the documented response is
infrastructure-level (Cloudflare WAF or rate limiting), not application-level IP
storage.

## API surface

All routes are on-demand (`prerender = false`) and return JSON with
`cache-control: no-store` and `vary: Cookie`.

| Route                     | Method   | Purpose                                                                                                                                                                 |
| ------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/comments/:slug`     | `GET`    | Published comments for one article, oldest first, as a flat list the island nests into threads. `canEdit` is true only for the caller's own comments inside the window. |
| `/api/comments/:slug`     | `POST`   | Create a comment, or a reply when `parentId` is a published top-level comment of the same article.                                                                      |
| `/api/comments/:slug/:id` | `PATCH`  | Change the body of the caller's own comment inside the window.                                                                                                          |
| `/api/comments/:slug/:id` | `DELETE` | Delete the caller's own comment inside the window.                                                                                                                      |

Parameters are re-validated inside the handlers, so slug syntax and UUID shape
are checked before any query runs. Responses use `{ok: true, ...}` or
`{ok: false, error, message}`; the message strings in
`src/lib/comments/domain.ts` are the ones the UI shows. A rejected create is one
of `cross_site` (403), `too_large` (413), `invalid_request` (400),
`verification_failed` (400), `invalid_parent` (400), a field-validation error
(400), `rate_limited` (429), or `unavailable` (503). Comment bodies, display
names, and tokens are never written to logs. Refusals are logged instead, as
`comment_refused` with the `operation` and a `reason` (`db_unconfigured`,
`turnstile_unconfigured`, `turnstile_unavailable`, `turnstile_invalid`), and
unexpected faults as `comment_<operation>_failed`, so a 503 that repeats across
articles is diagnosable from the platform logs. There is no dashboard, metric,
or health endpoint beyond `GET /api/comments/:slug`, which answers 503 while the
database is unreachable.

Public responses never include `author_token_hash`, `status`, or any ownership
field beyond the boolean `canEdit`. `is_author` is ignored on public input; only
`comments:reply` can set it.

Request bodies are capped at 16 KB and bodies are always rendered as text, so no
commenter-controlled field can produce HTML or script execution. Display names
and bodies are normalized on the way in: surrounding whitespace is trimmed, CRLF
line endings and trailing spaces within a line are normalized, and runs of three
or more newlines collapse to a blank line so a comment cannot stretch the page.

## Operator CLI

Moderation is local and explicit. No dashboard, no admin API, no browser-
reachable admin credentials. All commands print JSON and require the production
database configuration in an ignored `.env.local`.

| Command                                                                        | Purpose                                                                                                                                                                          |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run comments:list -- [--slug <slug>] [--include-hidden]`                  | Recent comments, newest first. Published only unless `--include-hidden`, which is how hidden and content-removed rows are reviewed.                                              |
| `npm run comments:hide -- <comment-id>`                                        | Set `status = 'hidden'`. Reversible, so no confirmation flag.                                                                                                                    |
| `npm run comments:restore -- <comment-id>`                                     | Set `status = 'published'`.                                                                                                                                                      |
| `npm run comments:delete -- <comment-id> --confirm-delete`                     | Permanently remove a comment and, if it has replies, those replies too. The output echoes every removed row (slug, display name, body excerpt) because the step is irreversible. |
| `npm run comments:reply -- --parent <comment-id> --body "..." --confirm-reply` | Post a public reply as the author. `--name` defaults to `Leon`.                                                                                                                  |

Hidden comments disappear from the public API immediately, including replies
attached to a hidden parent. A hidden comment cannot be replied to publicly, and
it cannot be edited or deleted by its original owner while hidden. Restoring a
reply whose parent is still hidden succeeds, but the reply stays invisible in the
public discussion until the parent is restored too.

The CLI treats an id that no longer exists as an error rather than a silent
success, and a reader who retries a delete whose response was lost is answered
`not_owned`: their comment is already gone, so their token matches nothing.

## Environment variables

| Variable                                    | Where                       | Purpose                                                                                                                                                                                                             |
| ------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL` (or `DATABASE_URL_UNPOOLED`) | Vercel + local `.env.local` | Neon connection. The same value the newsletter uses. Absent → the API answers 503 and the article renders normally.                                                                                                 |
| `TURNSTILE_SECRET_KEY`                      | Vercel + local `.env.local` | Server-side Turnstile verification. Read at runtime; absent → submissions are refused with 503 rather than accepted unverified.                                                                                     |
| `PUBLIC_TURNSTILE_SITE_KEY`                 | Vercel (build time)         | Public widget site key, inlined into the static article. Absent → the section shows `Discussion is temporarily unavailable.` in place of the form, skips the loading state, and still lists any comments that load. |

Create the Turnstile widget in Managed mode; the design assumes a visible
challenge for suspicious traffic only. The widget's hostname list must include
`leonlins.com` (and the local dev host when testing locally).

## Applying the migration

The discussion schema is additive and independent of the newsletter schema:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/comments/001_initial.sql
```

`ON_ERROR_STOP` is deliberate: without it `psql` reports an error and keeps
going, so a partly applied migration looks like success. The migration uses
`IF NOT EXISTS` throughout, so re-running it is a no-op rather than an error.

Apply it to a disposable Neon branch first, verify the table and constraints,
then apply it to production. The migration is safe to deploy before or after the
code: the API reports 503 while the table is missing, and articles render
normally regardless.

Applied to the linked Neon production branch (the same database the newsletter
uses) on 2026-09-18, after verifying the target from `.env.local`:

- `comments` exists with 10 columns, 4 indexes, and 14 constraints, and 0 rows.
- Re-running the migration only reports `already exists, skipping` for the table
  and each index, so it is a no-op.
- No newsletter table or row changed; the database went from 5 to 6 public
  tables.
- `GET /api/comments/list` moved from 503 to 200. A `POST` with no Turnstile
  token is refused with 400 `verification_failed`, which shows the production
  secret is configured; a foreign `Origin` is refused with 403 `cross_site` and
  an oversized body with 413 `too_large`. None of the probes wrote a row.

The Turnstile site and secret keys are set in Vercel production, so the section
renders the form rather than the configuration-error placeholder.

## Tests

`npm test` covers the discussion logic without a database: validation and
normalization, comment serialization, threading, Turnstile outcomes with an
injected `fetch`, and the full handler surface against a fake tagged-template
database (status codes, honeypot silence, cookie attributes, rate limiting,
hidden and deleted visibility, and no hash leakage).

`tests/comments-postgres.ts` is opt-in and is not part of `npm test`. It applies
the real migration to a real Postgres instance over a Unix socket and exercises
the SQL that no fake can prove: the constraints, the guarded reply insert, the
database-clock edit window, hard delete versus placeholder, and the cascading
operator delete.

```bash
COMMENTS_TEST_PG_SOCKET=/tmp/comments-pg-<name> \
  node --import ./tests/register-loaders.mjs --loader ts-node/esm tests/comments-postgres.ts
```

## Limitations

- Turnstile and the hosted Neon database cannot be exercised from CI. Unverified
  verification behavior is covered with an injected `fetch`, not against
  Cloudflare.
- Visual and interaction behavior (dark mode, mobile, keyboard order, hydration)
  is not covered by automated tests.
- The slug is validated syntactically, not against a registry of published
  articles. Any syntactically valid slug can receive comments through the API,
  so discussion data for a nonexistent article simply never renders. The POST
  endpoint therefore accepts comments for slugs that no article published.
- Ownership is per browser, so a reader who clears cookies cannot edit or delete
  older comments; they can ask for deletion instead.
- Comments belong to a slug, so renaming an article's slug orphans its
  discussion until the rows are updated manually, and there is no tooling for
  it because article slugs are permanent here.
- Posting is not idempotent. The button is disabled while a request is in
  flight, and an unanswered post reloads the list before the reader retries, but
  a comment stored by a request whose response never arrived can still be posted
  a second time. Deduplicating that would mean an idempotency key on the table.

## Deferred scope

Deliberately not built in V1: nested replies, notifications, voting, reader
accounts, comment search, an admin dashboard, IP storage for abuse control,
Redis or queues for rate limiting, and comment analytics beyond the three
interaction events the site's existing GA property already accepts.
